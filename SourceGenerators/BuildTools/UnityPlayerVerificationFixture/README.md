# Player verification fixture

Fixture of the Player gate (`SourceGenerators/scripts/verify-player.js`, Issue #57). It checks that clients generated by
the Source Generator run in an IL2CPP Standalone player and in a WebGL player, with and without Managed Stripping.

`verify-player.js` copies this directory to `Assets/PlayerVerification` of a temporary Unity project, installs the
add-on packages from `Packages/` of this repository, Newtonsoft.Json and System.Text.Json (UnityNuGet), and then:

1. `Editor/PlayerVerificationGenerate.cs` generates four clients through the public Source Generator provider from
   `Specs/player-spec.json` (Editor Writer, normalized spec bundle and the analyzer; nothing is checked in as generated
   output): `HttpNewtonsoft`, `HttpStj`, `UwrNewtonsoft` and `UwrStj` (HttpTransport x JsonSerializer). It also writes
   `Clients/<name>/Probe.cs` from `Templates~/ClientProbe.cs.txt`.
2. For each cell of the matrix, `Editor/PlayerVerificationBuild.cs` selects one client with a scripting define
   (`PV_HTTP_NEWTONSOFT`, ...; each client asmdef has a define constraint), sets the scripting backend and the
   Managed Stripping Level, and builds the player. Only the selected client is compiled into the player, so a stripping
   failure cannot be hidden or caused by another client.
3. The probe (a `RuntimeInitializeOnLoadMethod`) calls `getGadget` (GET) and `createGadget` (POST) of the generated
   client against the local server of the gate and reports a JSON result (`Common/PvRunner.cs`). Standalone players
   write the file given by `-pvReport` and exit with a non-zero code on failure; WebGL players post the report to
   `/report` of their own origin with the browser's `fetch` (`Common/Plugins/WebGL/PvReport.jslib`) so that a broken
   UnityWebRequest transport cannot hide the result.

## What the probe covers

`Specs/player-spec.json` has a string enum (`dark-blue` wire value), an integer enum, `date-time` and `date`, a map
(`additionalProperties`), an array, a `oneOf` union with a discriminator (`Shape`: `Circle` or `Square`), required
properties and constraints (`minLength`, `maxLength`, `minimum`, `maximum`).

- GET: the canned response is deserialized and every field is compared (enum, date-time, date, map, array, union).
- POST: the generated request serializer writes a body, the server checks the wire format (`player-gate-server.js`), echoes
  it, and the generated response deserializer reads it back.
- Constraint: a value outside `maximum` is rejected by the generated client before a request is sent
  (the server counts requests, so the gate also detects a request that was sent).

## Limits

- The server is on `127.0.0.1`, so the WebGL player and the server share an origin: CORS is not exercised.
- WebGL is built without compression and served by a plain static server; the browser is a headless Chrome/Edge
  (software rendering). Timers do not exist on WebGL, so the probe has no `Task.Delay`; the gate has its own time limits.
- The probe does not build a Development Player and does not use `link.xml` or `[Preserve]`: whether the generated
  code needs them is exactly what the High stripping cells test.
