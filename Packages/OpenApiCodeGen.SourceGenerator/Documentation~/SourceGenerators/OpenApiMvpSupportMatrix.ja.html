OpenAPI MVP 対応表

元の対応表

Source Generator (Beta) による生成はベータです。 利用前にこの対応表で入力仕様と生成されるAPIの制約を確認してください。

Editorの「Open Support Matrix」は、base packageに同梱したHTMLをブラウザーで開きます。 両パッケージにこの文書と参照資料のMarkdown／HTMLを同梱しており、公開タグやネット接続は不要です。 GitHub Actionsや外部仕様へのリンクを開く場合はネット接続が必要です。

目的と対象読者

この文書は、Rhycol.OpenApiCodeGen.SourceGeneratorで生成できるOpenAPI documentの MVP範囲を、API仕様の作成者とUnity利用者が判断するためのmatrixです。 対象はSource Generator providerで選択したlocal .json、.yaml、.yml document（extension case-insensitive）とHTTP(S) URLです。Editorは参照グラフ全体を canonical Normalized Spec Bundle v2へ正規化し、Analyzerは1 specIdにつき1 AdditionalFile だけを読みます。Bundle v1はAnalyzerの後方互換入力として読み込めます。

生成器は、wire formatに影響する未対応要素を黙って省略または推測しません。 Unsupportedに分類された要素と、Partialの制約外へ出た要素は診断を報告し、生成を完了しません。 入力・bundle・definitionの既存診断OACG001–OACG009に加え、semantic generationでは OACG100–OACG106を使用します。型名の重複をsuffixで解消した場合はwarning OACG107を、無視した要素があればwarning OACG108を報告します。

対応 記載した条件で生成・実行対象です。
一部対応 記載した部分だけを生成します。条件外は診断となります。
非対応 MVPの対象外です。診断となります。

入力と参照

項目 対応状況 条件・制約
入力document 対応 localの.json、.yaml、.yml file、またはHTTP(S) URL。local extensionはcase-insensitive。
OpenAPI version 一部対応 3.0.*と3.1.*のみ。
OpenAPI 3.1 schema dialect 一部対応 既定または明示的なhttps://spec.openapis.org/oas/3.1/dialect/baseのみ。入口・外部完全OpenAPI文書のjsonSchemaDialectとschemaの$schemaで別dialectを指定するとOACG101、不正なURIはOACG100です。
OpenAPI 3.2 / Swagger 2 非対応 document versionは受け付けません。
URL入力 対応 public/private/loopback、cross-host redirectを許可。userinfo、空白、非HTTP(S)、HTTPS-to-HTTP direct/redirectは拒否。Generateが明示的なfetch/refresh操作で、Docker fallbackはありません。
private GitHub repository 対応 https://raw.githubusercontent.comのURLのみ。SettingsのGitHub Tokenを、originが完全一致するリクエストとリダイレクト先にだけAuthorization: Bearerで送信。相対外部参照にも送信。トークンはプロジェクト外のユーザー設定に平文保存し、Bundle/manifest/診断には書き込みません。github.com、REST contents API、GitHub Enterprise Serverは対象外。
JSON/YAML semantic parity 対応 各normalizerがshared SpecNodeへ正規化し、同じsemantic/generation pipelineを通ります。
$ref 一部対応 OpenAPI/Schema上の参照位置にあるinternal reference、またはEditorがBundle v2のedgeへ解決したexternal reference。example/default/enum/拡張データ内の同名キーはデータとして保持。fragmentはemptyまたはJSON Pointer。
external $ref 一部対応 local external fileはreal/symbolic-link解決後もUnity project内。remote documentからlocal fileは不可。bare Schemaは可。参照先が完全なOpenAPI文書ならそのopenapi版とjsonSchemaDialectを検証し、入口とmajor.minor版が異なる場合はOACG101で拒否します。patch差は可。 Path Item $refの参照先がopenapi／swaggerを持たないbareなPath Itemファイルは、HTTP methodを持つか、$ref・parameters・servers・summary・descriptionだけを持ち、JSON Schema固有キーワード（type・properties・items・allOf・enum・requiredなど）を持たない場合にPath Itemとして内部の参照を収集します。1つでもschemaキーワードがあればbare Schemaです（$refだけのファイルはどちらでも同じ参照を収集します）。
unresolved / cyclic $ref 一部対応 解決できない参照はOACG102です。$refのaliasだけの循環（A→B→A）と、array／mapだけを経由して名前付きDTO／enumで閉じない循環はOACG103です。property・items・additionalPropertiesを経由するobject／enumの自己再帰・相互再帰は許可します。oneOf／anyOfのunionラッパーもobject・enumと同じ名前付きの型なので、unionを経由する再帰（Node: oneOf [Leaf, array of Node]など）も許可します。OACG104はBundle v1のexternal-reference互換診断です。
schema $ref target 対応 schemaの$refは#/components/schemas/<name>に限らず、任意のJSON Pointer（例: #/components/schemas/A/properties/b、$defs配下、拡張キー配下）と、Bundle v2のexternal documentの任意fragmentを指せます。型名はpointer末尾のtokenから付け（末尾が配列indexなら直前のtokenを前置）、名前の衝突は既存どおり連番とOACG107で解決します。inline定義と同じschemaを指す参照は別の型になる場合があります。parameters／responses／requestBodiesなど他のcomponent参照は従来どおり#/components/<section>/<name>だけです。
URL query / fragment 一部対応 queryはfetch identityに使いますが平文永続化しません。root URL fragment、userinfo、explicit file:は拒否。
URL format detection 対応 final URL extensionとContent-Typeが既知なら一致必須。片方だけ既知は可、両方不明・競合は拒否。content sniffing/hintはなし。

YAMLの対応範囲

YAMLは全仕様対応ではなく、source generatorが安全に正規化できる bounded YAML 1.2-compatible subsetです。subset外は黙ってJSONへ変換したり無視したり せず、YAML001–YAML015のsource-located diagnosticで拒否します。

block mapping / sequence 対応 indentationを使うmapping・sequence、nested/compact composition。compact continuationは2-space step。indentless sequenceと任意幅のcompact indentationは対象外。tabsはindentationに使用不可。
flow mapping / sequence 対応 nested、multiline、source orderを保持。flow collection内のblock scalarは対象外。
mapping key 一部対応 simple string keyのみ。duplicate、complex/non-string key、merge key <<は拒否。
comments / encoding 対応 comments、UTF-8 BOM、LF、CRLF。BOMはtreeから除きraw hashには含めます。
quoted / plain scalar 対応 single/double quoteとplain scalar。YAML 1.1 implicit bool/date等はstringとして保持。
引用付きscalarのUnicode escape 一部対応 隣接する高位・低位の\uサロゲート対と有効な\Uは非BMP文字を保持します。孤立・逆順・不一致のサロゲートescapeはBundle生成前に位置付きYAML006です。
JSON-compatible scalar 対応 null、true/false、RFC 8259 number（integer/real）、string。
literal / folded block scalar 一部対応 `
flow plain delimiter 一部対応 plain valueに,, [, ], {, }を含める場合はquote必須。URL scheme colon（https://）は受理。

tags / directives 非対応 explicit/custom tagとdirectiveは拒否。
document stream 非対応 multiple document（---/...による複数document）は拒否。

操作・パラメーター・レスポンス

項目 対応状況 条件・制約
HTTP method 対応 GET、POST、PUT、DELETE、PATCH、HEAD、OPTIONS、TRACE。
servers 一部対応 root serversは複数指定でき、各variables（default必須、enumは任意）も使えます。既定のコンストラクターはservers[0]の各variableをdefaultで置換したURLを使います（省略・空配列は/）。生成クライアントはpublic static IReadOnlyList<string> Servers（urlテンプレートの一覧）とpublic static string BuildServerUrl(int index, IReadOnlyDictionary<string, string>? variables = null)を持ち、展開したURLはbaseUrl引数として渡せます。BuildServerUrlは渡されたvariablesをenumで検証し、宣言のない名前・enum外の値はArgumentException、範囲外のindexはArgumentOutOfRangeExceptionです。urlの未宣言{x}はOACG101、defaultがenum外・空のenumはOACG100です。絶対URLはHTTP(S)のみで、FTPなどはOACG101です。//host/pathはHttpClient.BaseAddressのschemeで解決します。/pathと既定の/は同じoriginのrootから解決し、BaseAddressのpathとqueryを引き継ぎません。BaseAddressが必要な場合に未設定なら送信前にInvalidOperationExceptionです。明示的な空文字baseUrl overrideは相対URLとして扱います。相対server URLとoperation pathが/の場合、BaseAddressのqueryは1回だけ付加します。
path / operationのservers 一部対応 operation、Path Item、documentの順に優先してserverを選びます。operationまたはPath Itemにserversがあるoperationは、その先頭serverの各variableをdefaultで置換したURLを使います。コンストラクターのbaseUrlはdocument levelのserversだけを置き換え、path / operationのserversは置き換えません。実行時に差し替えるには、public IDictionary<string, string> OperationServerUrls（キーは生成メソッド名、値は展開済みのserver URL）へ設定します。このプロパティは、path / operationのserversを持つoperationがあるクライアントにだけ生成します。候補が複数あっても使うのは先頭だけです。候補の一覧と展開はpublic static IReadOnlyList<string> GetOperationServers(string operationName)とpublic static string BuildOperationServerUrl(string operationName, int index, IReadOnlyDictionary<string, string>? variables = null)（BuildServerUrlと同じenum検証）で行い、operation名には生成メソッド名の定数を持つpublic static class OperationNamesを使います。OperationServerUrlsのキーは生成メソッド名です（他のメンバーとの衝突回避で連番が付くことがあるため、OperationNamesの定数を使ってください。未知のキーは無視されます）。OperationServerUrlsは最初の送信より前（構成時）に設定してください。スレッド安全ではありません。
server URLの検証 一部対応 不正な絶対URL風・相対URL参照は位置付きOACG100、variablesに宣言のない{...}はOACG101です。不正な絶対URLを相対URLとして扱いません。有効なHTTP(S)・network-path・root-relative・path-relative形式は維持します。生のfragmentはoperation pathとの結合前に除き、エンコード済み%23はpath内に保持します。
parameter location 対応 path、query、header、cookieのparameterを扱います。
cookie parameter 一部対応 Cookieヘッダーを1本にまとめて送信します（複数のcookie parameterは; で連結し、parameterの識別子順）。formstyleで、explodeの既定はtrueです。名前はRFC 6265のcookie-name（token）でなければOACG100、値はRFC 3986のunreserved以外をpercent-encodeします（cookie-octetの部分集合）。配列・objectはexplode: trueならname=a; name=b／k=v; k=w、falseならname=a,b／name=k,v,k,wです（区切りの,はOpenAPIのformどおりで、RFC 6265の厳密なcookie-octetには含まれません）。HttpClientHandler.UseCookies=true（既定）ではCookieContainerの値が手動のCookieヘッダーと併用・上書きされることがあるため、cookie parameterを使う場合はUseCookies=falseにするか、CookieContainerに値を入れてください（Unity / Monoでの上書き挙動は実機確認が必要です）。Cookieという名前のheader parameterとcookie parameterの併用はOACG101です。
Parameter Objectの項目 一部対応 OpenAPI 3.0／3.1の標準項目とx-*拡張を認識します。requirdなどの未知項目は、path／operationのparameterや参照先でも位置付きOACG101です。schemaとcontentの併記はOACG100です。example／examples／allowEmptyValueは受理するだけで、送信値には影響しません。
parameter serialization 一部対応 style／explodeは次の組み合わせを対応します。path: simple（既定）・label・matrix、query: form（既定）・spaceDelimited・pipeDelimited・deepObject、header: simple、cookie: form。explodeの既定はformだけtrue、deepObjectは省略時true（falseの明示は仕様未定義でOACG101）です。locationに無効なstyleはOACG100、プリミティブへのspaceDelimited／pipeDelimited／deepObject、配列へのdeepObject、spaceDelimited／pipeDelimitedのexplode: trueは仕様未定義のためOACG101です。任意parameterのnullは省略し、明示的な空文字列はname=（query）として送信します。allowEmptyValueは省略される値の代替を表し、明示的な空文字列には適用しません。
array / object parameter 一部対応 OpenAPI 3.xの「Style Examples」表（color = blue,black,brown / R=100,G=200,B=150／空値／単一値）どおりに送信します（テストが表の全セルを検証します）。対象はプリミティブの配列（List<T>）と、プリミティブpropertyだけのobject（DTOまたはDictionary<string, T>）です。DTOは宣言したpropertyを名前の序数順にシリアライズします（nullのpropertyは省略）。additionalPropertiesがプリミティブのschemaなら、追加memberを宣言propertyの後にキーの序数順で続けます（値がnullのものは省略、プリミティブでない値はArgumentException）。additionalPropertiesが省略・trueの型なしopen DTOの追加memberは送りません。順序を指定したい場合はDictionaryを使ってください。配列要素のnullはArgumentExceptionです。空の配列・objectは何も送りません（pathは空文字列）。値の区切りとdeepObjectの[ ]は表のとおりそのまま出力します（|はSystem.Uriが%7Cにします）。header値はpercent-encodeしません。入れ子の配列・object、{}・JObject・union・複数型のparameterはstyleでは表せないためOACG101です（contentを使います）。
allowReserved 一部対応 allowReserved: true（queryのみ）は、予約文字:/?[]@!$&'()*+,;=と既存の%XX（RFC 6570の予約展開）を値でエンコードしません。#は区切りとしてURLのfragmentになりHTTP層で落ちるため、常に%23にします。名前と、allowReservedでないparameterは従来どおりエンコードします。
parameter content 一部対応 contentにはapplication/jsonまたは具体的なapplication/*+jsonを1件だけ宣言でき、値をJSON直列化してからpercent-encodeして送ります（path・query・cookieはpercent-encode、headerはエンコードなしでASCIIだけ）。schemaは任意（object・array・JToken・union可）です。style／explode／allowReservedの併記はOACG100、複数のmedia typeや他のmedia typeはOACG101です。
operationIdの省略 対応 operationIdのないoperationは、HTTP methodと、pathのセグメントを単語に分けたPascalCaseから決定的に命名します（{param}はBy＋名前）。GET /pets/{petId}はGetPetsByPetId、GET /はGetRoot、GET /report.{format}はGetReportByFormatです。ほかのoperationId（明示指定が優先）や同じ規則で生成された名前と重なる場合は、pathの序数順に2、3…を付けます。メソッド名としての衝突回避は通常の命名規則（AllocateUniqueName）が引き続き行います。明示したoperationIdの重複は従来どおりOACG106です。
Path Item $ref / components.pathItems 対応 pathのPath Item $refはinternalと、EditorがBundle v2のedgeへ解決したexternal documentの両方を辿ります（#/paths/...、OpenAPI 3.1の#/components/pathItems/<name>、他ファイルのfragment。ref先がさらに$refでもよく、循環はOACG103）。$refと併記できるのはsummary／description／x-*だけで、operation・parameters・serversなどの併記は仕様上未定義のためOACG101です。参照先のoperationはその参照元のpath keyで検証・命名します。components.pathItemsは3.1のみ受理し（3.0はOACG101）、参照されたものだけを解析します。
enum parameter formatting 対応 path／query／headerのstring enum値は専用のJson.NET serializerで宣言wire文字列へ変換し、ホストのJsonConvert.DefaultSettingsのconverterやcontract resolverを引き継ぎません。任意parameterのnull省略は維持します。
非有限数値parameter 非対応 path／query／headerのfloat／doubleにNaN・正負の無限大を渡すと、HTTP送信前にArgumentOutOfRangeExceptionです。任意parameterの省略と有限値は使用できます。
nested / untyped parameter 非対応 styleで表せないparameter（入れ子のarray/object、{}・JObject・union・複数型）は直接定義・多段$refともにOACG101です。contentを使うと任意のschemaを送れます。
required nullable parameter 非対応 path/query/headerのrequired: trueとnullableの組み合わせはOACG101です。参照チェーン全体を確認します。任意parameterのnull省略とDTOのnullableは維持します。
dot-only path segment 非対応 引数置換後のpath segmentが.／..（1回percent-decodeした表現を含む）なら、HTTP送信前にArgumentExceptionです。.hidden、a.b、...や通常の複合segmentは使用できます。
path template braces 一部対応 対応しない{／}は位置付きOACG100です。/pets}や/pets/{id}}も生成時に拒否します。
path keyの区切り文字 非対応 Pathsのキーに生の?・#があると、キーの位置でOACG100です。path内の文字ならpercent-encodeし、query値はquery parameterで宣言します。
header identity 対応 header名だけ大文字小文字を区別せず、operation側で上書きします。送信名はoperationの宣言を保持し、path/query名は区別します。
header parameter name 一部対応 HTTP field-nameのASCII tokenのみを許可し、空白・コロン・非ASCIIなど不正な名前はnameの位置付きOACG100です。
無視するheader parameter 一部対応 Accept、Content-Type、Authorizationは大小文字を問わず、OpenAPI仕様どおりparameterを無視し、名前の位置でOACG108のWarningを報告します。メソッド引数にもなりません。
header parameterの値 一部対応 生成クライアントが受け付けるのはHTABと印字可能ASCII（U+0020～U+007E）だけです。CR・LF・DEL・非ASCII・サロゲートはHttpClient.SendAsyncより前にArgumentExceptionです。省略した任意値は送信しません。
content専用header parameter 非対応 Allow、Content-Disposition、Content-Encoding、Content-Language、Content-Length、Content-Location、Content-MD5、Content-Range、Expires、Last-Modifiedは大小文字を問わずOACG101で拒否します（Content-Typeは上の無視対象です）。独自のContent-*名まで一律には拒否しません。通常headerの追加に失敗した場合も実行時にInvalidOperationExceptionです。
request body 一部対応 複数のmedia typeを宣言できます。application/json（パラメーター付きも含む具体的なapplication/<subtype>+json。application/*+jsonだけの宣言はOACG101で、具体型と併記された場合は具体型を選びます）、application/x-www-form-urlencoded、multipart/form-data、テキスト（text/*、application/xml・+xml・application/yamlでschemaがstringなどのscalar）、バイナリ（application/octet-stream、image/*、*/*などその他のmedia typeで、schemaがformat: binary・contentMediaType・省略）を扱います。type/subtypeを正規化して判定します。object schemaのapplication/xmlなど表せない組み合わせは該当位置のOACG101です。requestBody.required: falseならどのmedia typeでもnull引数は本文なしで送信します（<BodyParameterName>SpecifiedはJSONでschemaがnullableの場合だけです）。
multiple request media types 一部対応 複数のmedia typeは優先順位（JSON > form-urlencoded > multipart > text > binary）の最上位を主メソッド（operation名のまま）にし、残りは種別名の接尾辞を付けた追加メソッドとして生成します（<name>AsFormUrlEncoded、<name>AsMultipart、<name>AsText、<name>AsBinary。同じ種別が複数あれば2つ目以降は<name>As<MediaType>、例AsImagePng。名前が重なれば連番）。黙って捨てるmedia typeはありません。schemaが同じJSON media typeは1つにまとめ、最初の具体型をContent-Typeに送ります（schemaが異なればOACG105）。どの追加メソッドも同じparameter・戻り値・例外です。
multipart/form-data request 一部対応 object schemaの各propertyを1つのpartにします（DTOを引数に取り、readOnly propertyは送りません）。scalar・enum・format: byteはConvertToStringした文字列part（Content-Typeはtext/plain; charset=utf-8）、配列は同名のpartを要素ごとに複数、format: binary（またはcontentMediaType）のpropertyと、その配列はファイルpart（<ApiName>FileParameter、配列はList<<ApiName>FileParameter>）、objectなど入れ子の値はJSON part（Content-Type application/json）です。boundaryはMultipartFormDataContentが付け、Content-Dispositionは生成コードがRFC 7578に沿って組み立てます（name・filenameは引用符で囲み"と``をエスケープ、CR/LFはArgumentException、非ASCIIのpart名はUTF-8のpercent-encoding（netstandard2.0のHttpClientはヘッダーをUTF-8で書けないための妥協で、サーバーがpercent-decodeしなければフィールド名が一致しません。サロゲートペアは1コードポイントとして符号化します）、非ASCIIのファイル名はASCIIの代替名にfilename*=UTF-8''…を併記。ファイル名はFileParameter.FileNameがあるときだけ）。必須のpartがnullなら送信前にArgumentException、任意のpartはnullで省略します。multipartではencodingのstyle／explode／allowReservedを使わず（OACG108）、配列は常に1要素1partです。

successful response 一部対応 2xx（2XX範囲を含む）が成功です。全成功responseの本文contract（別名参照を終端まで解決し、実効nullable性・型・各値の境界が一致、inline enumの宣言順は無関係）が同じなら、従来どおり1つの型（本文なしはTask）を返します。contractが異なる場合は、status別の結果型を返します（下の「status別の結果型」）。従来のOACG105は、1つのresponse内の複数のJSON media typeでschemaが異なる場合だけです。 schema付きJSON成功本文の空・空白はnullableでもJsonSerializationException、JSON nullはnullable schemaだけで許可します。非nullableな配列要素がJSON nullなら、入れ子の配列とDTO内の配列も含めて拒否します。
status-keyed result type 一部対応 成功responseの本文contractが異なる、または2XX範囲に本文がある、またはdefaultだけ・responses省略などのoperationは、主メソッドが<OperationName>Response（名前が重なれば連番）を返します。StatusCode、宣言ごとのIs<Status>（IsStatus200、IsStatus2XX、IsStatusDefault）、本文があるstatusの型付きアクセサStatus200（その応答でなければnull）を持ちます。判定順は完全一致のstatus、2XX範囲、defaultです。status別のメソッドは追加しません。
text / binary response 一部対応 text/*・application/xml・+xml・application/yamlでschemaがscalar（stringなど）の成功本文はstring（ほかのscalarは宣言型へ変換。変換できなければJsonSerializationException）、application/octet-stream・image/*・*/*・schemaがformat: binaryまたは省略の成功本文はbyte[]です。本文の文字コードはJSONと同じ規則（charset・BOM）で読みます。HttpResponseMessageを返すオーバーロードとStreamを返すメソッドは生成しません（巨大なファイルはbyte[]に全読みします）。
response Accept header 一部対応 status別のresultを返すoperationと、JSON以外の本文または複数のmedia typeを持つ成功responseのoperationは、Acceptに処理できるmedia typeを優先順（JSON > text > binary）で送ります（先頭が主media type、残りはq=0.9、0.8…）。response内でschemaが主media typeと異なる型の別media typeは処理できないためOACG108で通知し、Acceptにも入れず、受信すると拒否します。受信したContent-Typeで処理を選び（先頭のmedia typeはContent-Typeなしにも使用）、宣言にないmedia typeはJsonSerializationExceptionです。従来のJSON単独のoperationはAcceptを送りません。
default-only / omitted responses / 3XX 一部対応 2xxがなくdefaultだけなら、defaultを成功contractとみなし、任意の2xxで成功します（2xxとdefaultが両方あればdefaultはエラーのcontractです）。responsesを省略（OpenAPI 3.1）または2xxがない場合は、任意の2xxで成功するTaskです（本文は読みません）。OpenAPI 3.0のresponses省略・空はOACG100です。3XXの宣言は受理しますが生成物には影響せず、HttpClientの自動リダイレクトに従い最終応答のstatusで成功・失敗を判定します（3xxの最終応答は2xxでなければ<ApiName>Exceptionです）。
本文を持てないレスポンス 非対応 HEADの全status、および成功204・205では非空のcontent宣言を位置付きOACG101で拒否します。Response Objectの参照先も検査します。空のcontentと本文なしは使えます。2XX範囲は型付き本文を宣言できます（status別の結果型）。
成功レスポンスのContent-Type 一部対応 そのstatusにcontent宣言がある場合、headerを宣言media typeと照合し、不一致・不正・複数値はJsonSerializationExceptionです。content宣言のない成功応答ではContent-Typeを照合しません。headerがない場合は従来どおり本文を読みます。.NETがheaderを先に正規化した場合、元の区切り空白は識別できません。
成功レスポンスのJSON 一部対応 RFC 8259の構文、重複しないproperty名、宣言schemaに合うJSON token型を本文と入れ子の値で検査します。closed DTO（additionalProperties: false）の未宣言propertyを拒否し（open DTOとmapは許可し、宣言した値型を検査します）、Json.NETの$id／$ref／$values参照メタデータを互換拡張として維持します。配列schemaでも$id／$valuesで包まれたJSON objectを受け付け、配列要素を検査します。整数は数学的整数値の1.0／1e0を許可し、小数・CLR型の範囲外を拒否します。型不一致・未知property・非有限float／doubleはJsonSerializationExceptionです。DTOの必須property（writeOnlyを除く）の欠落とenumの未宣言値も、変換前のJSON検査でJsonSerializationExceptionにします（従来はJson.NETの変換時に拒否）。 受信JSONの構文検査は通常最大64階層で、ホストがJsonConvert.DefaultSettings.MaxDepthに正の値を設定した場合はその値を使い、nullまたは未指定なら64階層を維持します。
レスポンスJSONの変換設定 一部対応 生成するレスポンスserializerは独立したJson.NET設定を使い、ホストのJsonConvert.DefaultSettingsにあるconverter・contract resolverは検査済みの値を変えません。引き継ぐのは正のMaxDepthだけで、未指定・null・不正値なら64です。生成DTOのconverterと対応済みの$id／$ref／$valuesメタデータは維持します。
成功レスポンスDTOのメタデータ名 非対応 DTO propertyに$id、$ref、$type、$valuesを宣言すると、そのpropertyの位置でOACG100です。リクエスト専用DTOでは使用できます。schemaで宣言していないJson.NET参照メタデータの互換動作は維持します。
error/default response 一部対応 本文の構造・参照を検証し、成功本文のDTO生成制限は適用しません。4xx・5xx・4XX・5XX・defaultのJSON本文はschemaが生成できれば<ApiName>Exceptionから取得できます（下の「typed error」）。生成できないschemaは受理しますが、その位置でOACG108のWarningを報告し、本文はResponseBodyの文字列だけです。本文を宣言していない（またはJSON本文を持たない）4xx・5xx statusは「型なし」として扱い、defaultの型にはフォールバックしません（defaultは未宣言のstatusにだけ適用）。JSON以外のmedia type（*/*などのwildcardを含む）も受理します。例外は実際の本文を保持します。
typed error 対応 <ApiName>Exceptionは従来のStatusCode・ResponseBody（文字列）を保ったまま、宣言されたJSON本文を逆シリアル化したobject? Errorとbool TryGetError<T>(out T value)、失敗理由のException? ErrorDeserializationExceptionを持ちます。statusの選択は完全一致、4XX／5XX、defaultの順です。逆シリアル化に失敗（不正なJSON・必須property欠落など）しても例外を握りつぶさず、ResponseBodyに本文を残してErrorはnull、失敗はErrorDeserializationExceptionに残します。既存の2引数コンストラクターは変わりません。エラーresponseのheaderは公開しません。
response extension 対応 operationのResponses Objectではx-*を除外します。components.responsesのx-*名は通常のResponse/Referenceです。
response header 一部対応 成功responseのheadersは、そのoperationに<name>WithHttpInfoメソッド（追加メソッド。<Name>HttpInfoクラスを返す）を生成して公開します。StatusCode、raw Headers（IReadOnlyDictionary<string, string[]>、大小文字を区別しない）、Data（通常のメソッドの戻り値）と、宣言headerごとの型付きプロパティ（X-Rate-LimitはXRateLimit）を持ちます。headerはsimplestyle（scalarとscalarの配列。配列はカンマ区切り）、型はint・double・bool・DateTime・Guid・enumなどをinvariant cultureで読み、不正な値とrequiredの欠落はJsonSerializationExceptionです。通常のメソッドは同じ検査を行いDataだけを返します（headerを宣言したoperationだけが対象で、ほかのoperationにWithHttpInfoは生成しません）。header objectのcontent、objectのheader、style: simple以外はOACG101、Content-Typeは仕様どおりOACG108で無視します。エラーresponseのheaderは検証だけで公開しません。headersはobjectが必要で、scalar・array・nullは位置付きOACG100です。
components.headers 対応 components.headersと、responses・encodingのheaderからの#/components/headers/<name>参照を解決します（参照先は通常のHeader Objectと同じ規則で検証します）。
Response Objectの項目 一部対応 description・headers・content・links・x-*拡張だけを認識します。contentsなどの未知項目は、成功・エラー・参照先の応答でも位置付きOACG101です。

status codeはASCII数字で検証します。属性付きのジェネリックclassはOACG005で拒否します。

Security

項目 対応状況 条件・制約
components.securitySchemes 対応 apiKey（inはheader／query／cookie、name必須。header・cookieのnameはHTTP tokenに限り、headerのnameがCookieまたはContent-*（大小文字を問わない）の場合はnameの位置付きOACG100です）、http（scheme必須。bearer／basic／その他の任意のscheme）、oauth2（flowsと各flowの必須URL・scopes）、openIdConnect（openIdConnectUrl必須）、mutualTLS（OpenAPI 3.1以降）を解析します。scheme自体の$ref（internal）も辿ります。必須項目の欠落、inの不正値、未知のtype、未知のoauth2 flow、3.0のmutualTLSは不正な項目の位置付きOACG100です。
security requirement 対応 root securityとoperation securityを評価します。operationのsecurityはrootを上書きし、security: []はそのoperationの認証をなくします。配列はOR、1つのobjectに並べた複数のschemeはANDです。{}（匿名可）は認証を要求しないrequirementとして扱い、他のrequirementより優先しません。未定義のschemeを参照すると、その参照の位置付きOACG100です。scopesは文字列配列として検証し、XML docにだけ出力します（送信前に検証・取得しません）。OpenAPI 3.1の「scheme名をURIで参照する」形は未定義schemeとしてOACG100です。
資格情報API 対応 schemeごとにclientのpublicプロパティを生成します。名前はcomponents.securitySchemesのキーをPascalCaseにした後ろに種別の語を付けます（衝突時は数字を付けて一意にします）。apiKey: string? <Scheme>ApiKey。http bearer／oauth2／openIdConnect: string? <Scheme>AccessTokenとFunc<CancellationToken, Task<string?>>? <Scheme>AccessTokenProvider。http basic: string? <Scheme>Usernameとstring? <Scheme>Password。その他のhttp scheme: string? <Scheme>Credentials。mutualTLSは何も生成しません。XML docにschemeのdescription、bearerFormat、oauth2のflowとscopes、openIdConnectUrlを出力します。簡略名（BearerTokenなど）は生成しません。
requirementの適用 対応 各operationの有効なrequirementを文書順に調べ、含まれるすべてのschemeに資格情報が設定済みの最初のrequirementを適用します（送信ごとに評価します）。どのrequirementも満たせないとき、および{}だけのときは認証なしで送ります（例外にはしません）。apiKey／bearer／basic／その他のhttp schemeは、nullまたは空の資格情報を未設定として扱います（basicはUsernameがnullのときだけ未設定で、Passwordがnullなら空のpasswordです）。
apiKey の送信 対応 header: nameのheaderとして送信します。query: 既存のquery parameterの後ろにname=value（名前と値をpercent-encode）を足します。cookie: parameterのcookieと合わせて1本のCookieヘッダーにします（値はpercent-encode）。同名のheader parameterがあっても、そのschemeに資格情報が設定されているときはsecurityの値が優先します（設定されていないときはparameterの値を送ります）。cookieも同様で、cookie apiKeyに資格情報が設定されているときは同名のcookie parameterの部分を除き、その名前はCookieヘッダー内で1回だけ送ります。
http の送信 対応 bearer: Authorization: Bearer <token>。basic: Authorization: Basic <base64(username:password)>（UTF-8でバイト列にしてからBase64。Usernameに:を含むとInvalidOperationExceptionです）。その他のscheme: Authorization: <scheme> <credentials>（schemeは仕様に書かれた表記のまま）。Authorizationが複数のschemeから出るANDでは最後のschemeが勝ちます。送信するheader値は既存のheader parameterと同じ規則（ASCII）で検査し、違反はArgumentExceptionです。
oauth2 / openIdConnect 一部対応 外から渡されたtokenをBearerとして送るだけです。flowによるtoken取得、更新、OpenID Connect discoveryは行いません（URLやscopesはXML docのみ）。tokenは<Scheme>AccessTokenに設定するか、<Scheme>AccessTokenProviderで供給します。providerは設定されていればプロパティより優先し、送信ごとにそのリクエストのCancellationToken付きで呼びます。providerがnullまたは空を返したときはプロパティを使います。
mutualTLS 一部対応 受理しますが、クライアント証明書の設定はclientではなくHttpClientHandlerで行います（XML doc・生成コードでは何も送りません）。送るものがないため、mutualTLSだけのrequirementは匿名と同じ扱いで、他のrequirementを妨げません。このためOACG108のWarningは出しません。
資格情報の取り扱い 対応 資格情報プロパティはスレッドセーフではありません（XML docに明記）。リクエストごとに1回だけ読みます。生成コードはログを出さず、例外メッセージに資格情報を含めません（header名とscheme名だけを使います）。

$ref sibling 一部対応 注釈、literalデータ、x-*と3.0のnullableは保持して参照のままです（3.1でtypeだけ、またはnotを併記した場合も参照のままです）。OpenAPI 3.1でproperties、required、additionalProperties、allOfなどの構造を併記するとallOf: [ {$ref}, {siblings} ]として扱い、下のallOfの規則で1つのDTOへ平坦化します。3.0では従来どおり、合成が必要な兄弟keywordを該当位置のOACG101で拒否します。
nullable 一部対応 OpenAPI 3.0のnullable、OpenAPI 3.1のtype: [<type>, null]。
optional nullable DTO property 対応 未代入はJSONから省略し、null代入は明示的なJSON null、値の代入はその値を送ります。生成される<PropertyName>Specifiedをfalseへ戻すと再び省略します。
optional non-nullable DTO property 対応 JSONで省略できますが、明示的なJSON nullを受信するとJsonSerializationExceptionです。未設定値をシリアライズすると省略します。
required non-nullable DTO property 対応 参照型の必須項目がnullならシリアライズ中に検出し、リクエストを送信しません。入れ子のDTOにも適用します。必須nullable項目のJSON nullと必須値型の既定値は送信できます。
scalar format 一部対応 integerは通常int、int64はlong。numberは通常double、floatはfloat、decimalはdecimal。date、date-time、uuidはDateTime、DateTimeOffset、Guidへmappingします。成功レスポンスでは変換前にそれぞれ日付、タイムゾーン付き日時、ASCIIの8-4-4-4-12形式を字句検査します。字句が正しくてもCLRで表せない時刻・うるう秒などは変換時に拒否される場合があります。 byteはbyte[]にmappingします（成功応答はbase64を検査）。
formatの綴り 一部対応 int64、float、decimal、date、date-time、uuid、byte、binaryは小文字の完全一致だけを特別扱いします。大文字を含む未知の綴りはschemaの基底型として扱います。
リクエスト数値 対応 float／doubleのNaN・正負の無限大は本文直下・配列・DTO内ともHTTP送信前にJsonSerializationExceptionで拒否します。省略指定した任意項目は検査しません。
map / free-form object 対応 propertiesがなくadditionalPropertiesがschemaならDictionary<string, T>です。成功応答では各値を検査し（非nullableな参照型のnull、型不一致、Json.NETの$id／$ref／$type／$valuesキーを拒否）、requestでは値の型に応じたnull・非有限数を検査します。propertiesがなくadditionalPropertiesが省略またはtrueのtype: object（free-form）はJObjectです。
any / type inference 対応 {}、OpenAPI 3.1のboolean schema true、type: "null"、およびnull以外の型を複数持つ3.1の型配列（例: ["string","integer"]）はJTokenです（JSON nullを受け付けるため常にnullable）。typeを省略した場合は、properties／additionalPropertiesがあればobject、itemsがあればarray、enumの値からstring／integer、constの値からその型を推論します。boolean schema falseはOACG101です。parameterの{}や複数型はOACG101のままです。
schema assertions 非対応 生成モデルが保持しないpattern、minLength、minimum、minItemsなどのassertionは、そのkeywordの位置でOACG101です。説明用annotation、default、x-*は許可します。constと$defsはOpenAPI 3.1のkeywordで、3.0ではOACG101です。
const 一部対応 OpenAPI 3.1のscalar const（string／integer／number／boolean）。成功応答では値の一致を検査し（integer／numberは数値として比較するため2.0は2と等価）、不一致はJsonSerializationExceptionです。request DTOでは、string／整数／浮動小数／decimal／booleanのDTO propertyの初期値になるだけで、request側で値は検証しません（nullableな任意propertyは初期値の対象外）。object／array値はOACG101、schema型と合わない値はOACG100です。nullや単一のscalar型を持たないschemaのconst、enumと併記したconstはOACG108で無視します。
description / title / deprecated / default 対応 titleとdescriptionはDTO・property・enum（とmember）のXML docへ出力します。deprecated: trueはschemaとpropertyに[Obsolete]を付けます（生成コード内は#pragma warning disable CS0612, CS0618）。defaultはXML docだけで、wire contractは変えません（object／arrayのdefaultは無視）。operationのdeprecated: trueは生成メソッドへ[Obsolete]を付け、summaryは<summary>、descriptionは<remarks>に出します。parameterのdeprecatedとdescriptionは<param>のXML docに反映します（C#の引数には[Obsolete]を付けられません）。
allOf 一部対応 各partのproperties・required・additionalPropertiesを1つのsealed DTOへ平坦化します（$ref先は再帰的に展開し、入れ子のallOfも可）。requiredは和集合です。closednessは合成後に評価します。どれか1つのpart（または3.1の$refsiblings）がadditionalProperties: falseならDTO全体をclosedにし、許可するpropertyは全partのpropertiesの和集合です（partごとのfalseを単純合算して、他のpartのpropertyを拒否することはしません）。additionalPropertiesがschemaのpartがあればtyped open（複数あれば同じschemaが必要）、それ以外はopen objectです。同名propertyの型がpart間で異なればOACG101（2つ目の宣言の位置、1つ目はadditional location）、同じ型なら統合します。partがobject以外のtype・items・enum・constを持つ場合、partがoneOf／anyOfを持つ場合（discriminator付きのbaseを除く）はOACG101、どのpartも宣言しないrequiredはOACG100、allOfの循環はOACG103です。part内のnotはOACG108で無視します。allOf: [ {$ref} ]の1要素にdescription・nullableなどの注釈だけを併記する定番の形は、新しい型を作らない参照です（nullableも保持）。
oneOf / anyOf + discriminator 一部対応 discriminator付きのoneOf／anyOfは、sealedなunionラッパークラス（例: Pet）とメンバーのDTO（Cat、Dog）を生成します。メンバーのDTOはラッパーを継承しない通常のsealed DTOです。ラッパーに付けるJsonConverterが具象DTOの書き出しで再入して無限再帰することはありません。ラッパーはFromCat(Cat)・暗黙変換・TryGetCat(out Cat)・AsCat()、保持している具象値Value、選択値DiscriminatorValueを持ちます。メンバーは$refでobjectを指す必要があります（inline、またはobject以外は、メンバーの位置のOACG101）。discriminator値はmapping（値はschema名、#/components/schemas/Xのinternal pointer、またはoneOf内の$refと同じ文字列）と、mappingのないメンバーの暗黙値（schema名）で解決します。メンバーにmappingがあればその値だけが有効で、複数あれば最初の値を送ります。他ファイルを指すmapping、メンバーでないschemaを指すmappingはOACG101、複数のメンバーに同じ値を割り当てるとOACG100です。メンバーDTOがdiscriminator propertyを宣言していなければ生成側が任意のstring propertyとして追加し、選択値が1つならDTOの初期値にします（宣言済みのstring propertyにも同じ初期値を付けます）。この初期値は検証せず、requiredにもしないため、unionを経由しない単独利用のDTO（discriminatorを持たない応答など）は有効なままです。discriminatorの有無と値の検査はunion（converterと成功応答の契約検査）だけが行います。requestはunionが常に選択値を書きます。成功応答は値でメンバーを選び、未知・欠落・stringでない値はJsonSerializationExceptionで、選んだメンバーのDTO検査（closedなら未宣言property、必須property）も行います。ラッパーのJsonConverterクラスにはIL2CPP用のPreserveAttributeを付けます。
discriminator付きbase（継承） 一部対応 oneOf／anyOfを持たずdiscriminatorだけを持つschema（子がallOf: [ {$ref: base}, … ]で継承する形）は、mappingの対象と、同じdocumentのcomponents.schemasでallOfにbaseを直接$refしているschema（孫まで）をメンバーとするunionになります。baseのpropertiesは子のDTOへallOfで平坦化されます。base自身は（値がPetなどでも）メンバーにならず、そのdiscriminator値は未知の値として拒否します。子もmappingもないdiscriminatorはOACG108で無視します。他のdocumentのschemaは子として探しません。oneOf＋discriminatorを持つschemaを子がallOfで継承する形では、子はそのschemaのpropertiesだけを引き継ぎ、oneOfは引き継ぎません。
oneOf / anyOf（discriminatorなし） 一部対応 type: nullだけの部品を除いた候補が1つなら、その型のnullableに正規化します（[X, null]）。それ以外は成功応答の生のJTokenを保持するunionラッパーです（FromJToken(JToken)、ToJToken()、候補ごとのFromX(T)・暗黙変換・TryGetX(out T)・AsX()。string／integerなどのプリミティブ候補も扱います。アクセサ名は型名で、String、Int32、CatListなどです）。成功応答は候補ごとに既存のJSON契約検査を試し、oneOfはちょうど1件、anyOfは1件以上の一致を求めます（違反は一致件数つきのJsonSerializationException）。一致は構造検査（型、closed DTOの未宣言property、必須property、enumの値、const）で決めます。oneOfで複数の候補が一致した場合は、応答JSONのすべてのpropertyを宣言している候補（closedとみなした一致）に絞り込み、ちょうど1件ならそれを選びます（open DTO同士が重なる典型ケース）。絞り込んでも1件にならなければエラーです。integerとnumberのように区別できないoneOfや、同じpropertyだけを持つ候補は失敗し得るので、required・additionalProperties: false・discriminatorで区別できるようにしてください。anyOfは絞り込まず1件以上の一致で足ります。TryGetXも同じ規則で候補を選びます。TryGetXは、FromXで渡した値か、保持しているJSONをJson.NETの厳密な設定（未宣言memberはエラー）で変換できるかで判定します。requestは渡された候補値またはJTokenをそのまま直列化します（候補値のrequest検査は行いません）。同じschemaへproperties／requiredなど形を決めるkeywordを併記する、allOfとoneOf、oneOfとanyOfを併記する場合はOACG101です（keywordはメンバー側へ移します）。unionのparameterもOACG101です。
not 一部対応 成功応答の検査だけで評価し（notのschemaに一致した値をJsonSerializationExceptionで拒否）、生成する型は変えません。schema・property・$ref先のどこのnotも対象で、一致は構造検査（型、enum値、const、DTOの形）で決めます。requiredだけのような形を持たないnot、boolean schema、再帰するnot、未対応の要素を含むnotは、全値を拒否してしまうか判定できないためOACG108で無視します。requestでは評価しません。
readOnly / writeOnly 対応 readOnlyなDTO propertyはrequestへ送信せず（生成されるShouldSerialize<Name>()がfalse）、requestのrequired検査からも外します。成功応答ではschemaのrequiredどおり必須です。writeOnlyなpropertyは成功応答で欠落しても許可し、requestではrequiredのままです。$ref先のschemaに付いたreadOnly／writeOnlyも、参照するpropertyに適用します。readOnly propertyの値はrequestで検証もしません。Unity IL2CPPのmanaged strippingでreflection専用メンバーが削除されないよう、ShouldSerialize<Name>()とAdditionalPropertiesにはinternalなPreserveAttributeを付け、ShouldSerialize<Name>()はEditorBrowsable(Never)にします。
format: byte 対応 byte[]（Json.NET標準のbase64）へmappingします（従来はstring）。成功応答は文字列かつ有効なbase64であることを検査し、path/query/header parameterは標準base64文字列で送ります。
format: binary 一部対応 multipartのファイルpart（<ApiName>FileParameter）、バイナリのrequest本文（byte[]）、バイナリ応答（byte[]）で使えます。JSONの本文・DTO（JSON応答を含む）・parameter・header・form-urlencodedの値で参照されると、binaryのschemaの位置でOACG101です（binaryを含むschemaをcomponentsに置くことは可能で、使われた場所で判定します）。3.1のtype: string＋contentMediaType（contentEncodingなし、JSON・text・xml以外）も同じ扱いです。大文字小文字の違うformatは従来どおり通常のstringです。

$refと併記できる注釈・データのキーは$comment、default、deprecated、 description、example、examples、externalDocs、readOnly、summary、title、writeOnly、xml、x-*です。 OpenAPI 3.0では既存互換としてnullableも扱います。

リクエストJSONのformat: dateはyyyy-MM-ddへ変換します。公開型のDateTimeは維持し、 date-timeのDateTimeOffsetにはdate用converterを適用しません。

生成結果と利用上の制約

生成結果は次のpublic API contractです。

  • public mutable sealed DTO（Json.NET attribute使用）
  • 任意かつschema上nullableなDTO propertyの<PropertyName>Specifiedによる存在状態の管理
  • 任意かつschema上nullableなrequest bodyの<BodyParameterName>Specifiedによる明示的なJSON null送信
  • 宣言したwire文字列を完全一致で扱うstring enum converterとList<T>
  • oneOf／anyOfのsealed unionラッパークラス（FromX／TryGetX／AsX、discriminatorなしはFromJToken／ToJToken）と、internalなJsonConverter
  • injected HttpClientを使うasync client API。documentまたはexplicit base URLを指定するconstructorを使用可能
  • path/query/header/body、JsonConvert、CancellationToken、宣言された2xx response handling
  • request本文のmedia type別メソッド（<name>AsMultipartなど）、ファイルpartの<ApiName>FileParameter、status別の結果型<OperationName>Response、<name>WithHttpInfoと<Name>HttpInfo
  • generated <ApiName>Exception（Error／TryGetError<T>／ErrorDeserializationExceptionを追加）

生成モデルは、raw JSON/YAMLを各normalizerでnormalized bundleへ変換した後、OAS semantic parserとinternal reference resolverを通し、 Roslyn非依存のgeneration modelを作ってから、Roslynでparseしたdeterministic source emitterへ渡します。 emitterの結果をAddSourceします。serializer/backendは固定で、generated clientは Newtonsoft.JsonとSystem.Net.Http.HttpClientを使用します。Docker providerは別providerであり、 fallbackまたは切替は行いません。

生成物はhand-editするsourceではなく、再Generateされるpublic contractです。spec IDを含むhint nameは stableで、generated nameはordinalのdeterministic namingとsuffixによるcollision resolutionを使用します。 複数specでDTO名が重なる場合は、generated namespaceを分けてください。current generated typeは namespace-levelのため、同じnamespaceには共存できません。

apiNameが生成クライアントの固定メンバー名と一致するとOACG005です。予約名は _httpClient、_baseUrl、DateOnlyJsonConverterInstance、CreateRequestUri、 CombineAbsoluteUri、CombinePaths、CombineQueries、AppendQuery、 SplitPathAndQuery、ValidatePathSegments、CreateJsonContent、 ConvertToString、DateOnlyJsonConverterです。 schemaの項目名が別項目のCLR名にSpecifiedを付けた名前と衝突する場合、JSON上の名前を保ったまま CLR名に番号を付けます。Json.NETがschemaのboolean値を存在フラグと誤認することを防ぎます。
